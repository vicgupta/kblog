<p>A coding agent writes code and stops at a pull request. A <strong>software factory</strong> is the production system around the agent that turns that code into something shippable: standardized inputs, a defined assembly path, automated quality control, and evidence-backed outputs. In 2026 the idea has come back in agent-native form — fleets of AI coding agents as the workers inside the pipeline, engineers defining intent and reviewing evidence. Factory.ai's <a href="https://factory.ai/news/software-factory">Factory 2.0 manifesto</a> put it in one line: <em>"This system will be built by engineers, and in turn will build their software."</em></p>
<p>This post is the technical anatomy: what the stations are, what the under-appreciated <strong>utilities layer</strong> must cover, which patterns actually ship, where factories fail, and a concrete path to building one — including a local one you can boot in one command.</p>
<h2>Why now: the bottleneck moved</h2>
<p>Writing code stopped being the hard part. Everything after it got harder. AI-authored pull requests wait <strong>4.6x longer for first review</strong> (LinearB, across 8.1M PRs), and <strong>45% of deployments carrying AI-generated code run into problems</strong>. Throughput went up; review and deploy did not keep pace. The factory exists to industrialize the downstream: confirm each change actually works, and get it into production without hand-writing cloud configuration per change.</p>
<p>The data points piling up in 2026 all point the same way: BCG Platinion declared the "Agentic Software Factory era" open with practitioner-reported <strong>3–5x productivity gains</strong>; Spotify's engineering account reports <strong>1,500+ agent-generated PRs merged</strong> with 60–90% time savings on migration workflows; OpenAI described an internal beta built from an empty repo by three engineers steering agents — roughly a million lines including tests, CI, docs, and observability, with no manually written code. The assembly line works. The question is what it is bolted to.</p>
<h2>Anatomy I: the stations</h2>
<p>Every factory in the wild implements some version of this loop — signals in, verified software out, and the monitoring of that software generating new signals:</p>
<pre><code>signals (bugs, feedback, specs)
  → triage → plan → implement → test
  → review → secure → release → monitor
  → (new signals)
</code></pre>
<ul>
<li><strong>Intake/triage.</strong> Route signals to planned changes. Cheap classifiers and intent routing live here — decide whether a request needs a DB lookup, a full agent, or a human.</li>
<li><strong>Plan/build.</strong> One or many agents implement against isolated infrastructure (more below). Parallel tracks for complex tasks; single-threaded flow for the rest.</li>
<li><strong>Validate.</strong> Tests, type checks, static analysis, security scans (STRIDE/OWASP/secret sweeps), contract-drift checks. Every change validated before it ships.</li>
<li><strong>Review.</strong> Human or adversarial-agent review with severity tiers (P0–P3), inline comments, and per-repo guidelines. This is the station most teams under-build — see the failure modes section.</li>
<li><strong>Release/operate.</strong> Provision, deploy, monitor. Merging provisions the same resources the change was validated against. Humans stay on judgment: publish remains a human act in every sane design.</li>
<li><strong>Learn.</strong> Every session, review, and incident feeds back. The router learns which model handles which task; findings from production feed the next plan. This is the compounding edge — the factory gets more capable the more you run it, and that capability stays inside your walls.</li>
</ul>
<h2>Anatomy II: the utilities (the part everyone skips)</h2>
<p>TrueFoundry's <a href="https://www.truefoundry.com/blog/software-factory-agentic-enterprise-guide">agentic factory guide</a> makes the manufacturing analogy explicit: a physical factory is only as good as its power, plumbing, metering, and safety. The agent factory's utilities are:</p>
<ul>
<li><strong>Isolated environments per agent.</strong> Each change gets its own environment with the databases and queues it needs — Encore's <a href="https://encore.dev/articles/what-is-an-ai-software-factory">walkthrough</a> shows the pattern: the agent declares a Postgres DB and a Pub/Sub topic in application code, the factory provisions them in the agent's sandbox, the agent migrates, calls the endpoint, and watches the row persist and the event publish <em>before</em> opening the PR. Twenty agents run without one migration breaking another's tests. This matters most for infrastructure code, where models that ace language benchmarks collapse on infra benchmarks.</li>
<li><strong>Model supply + routing.</strong> No single model leads on every axis. The factory routes each task to the model that handles it best and adopts new ones without changing the workflow. Model independence is a requirement, not a preference.</li>
<li><strong>Credential handling + identity.</strong> Centrally managed credentials injected into tool calls (never embedded in agent definitions), per-user OAuth where supported, and a clear answer to who-did-what when an agent acts on a user's behalf. Anything the gateway doesn't mediate — direct APIs, shell, CI bypass paths — needs its own controls.</li>
<li><strong>Quality control as a system.</strong> Repo tests, static analysis, sandbox/egress controls, merge policy, evaluators — separate parts, one bar. Deterministic checks (gates that always run) beat agentic checks (a second model eyeballing the first) for the load-bearing walls.</li>
<li><strong>Telemetry + spend metering.</strong> Execution traces, per-request evidence, and hard budget rules that block after limits — not just dashboards. Measure outcomes (shipped, reliable software), not tokens. Lines and PRs opened say nothing about whether you ship better software.</li>
<li><strong>Sovereign deployment.</strong> Same platform in managed cloud, your cloud, your datacenter, or air-gapped. The factory learns from itself wherever it runs, and the learning stays with you.</li>
</ul>
<h2>Patterns that actually ship</h2>
<p><strong>1. The conveyor (station pipeline).</strong> Intake → plan → build → review, with queue depth as natural backpressure. OpenRig ships this as <code>conveyor</code> — four seats, two Claude and two Codex, bootable with <code>rig up conveyor</code>. It is the smallest shippable factory and the right starting shape: a real handoff path with a small footprint.</p>
<p><strong>2. The specialist chain (12 agents, 3 checkpoints).</strong> The <a href="https://github.com/dewantrie/ai-software-factory">dewantrie/factory</a> pattern: one prompt library rendered into platform files (Claude Code, Kiro, Codex CLI) from a single source of truth, 12 single-job specialists (backend, frontend, tests, migrations, infra, docs…) each in a fresh context window with restricted tools, an orchestrator skill that routes but never edits, and three human checkpoints — approve the story, approve the brief, review the diff. Path scoping is <em>enforced</em> by hooks on Claude Code, prompt-only elsewhere. The lesson generalizes: tool scoping prevents agents from doing each other's work.</p>
<p><strong>3. The self-driving loop (dogfood decoupled).</strong> OpenRig's <code>factory-rsi</code> (v0.4.6+): a <code>plan → implement → qa_check → review → release</code> inner loop with loop guards, running out-of-band against the shipped product and feeding recorded findings into the next plan — while publish stays behind a human <code>release_signoff</code> gate. Autonomy inside, human on the consequential edge.</p>
<p><strong>4. The governed enterprise factory.</strong> The <a href="https://github.com/deepkawal/software-factory">deepkawal/software-factory</a> reference architecture: domain-neutral SDLC core plus regulated overlays — design-time governance (privacy, security, AI-governance, vendor risk, release evidence before implementation), runtime control-plane governance (model routing policy, prompt/tool policy, MCP access, sensitive-data filtering, token budgets, audit logs), and domain packs (fintech, healthcare). Machine-readable capability profiles decide which controls, reviewers, and evidence each release needs. The differentiator, as its author notes: as models converge, <em>context</em> — docs, ADRs, standards, conventions, organizational memory — is the real asset.</p>
<p><strong>5. Scheduled Droids (recipes on cron).</strong> Factory.ai's twelve starting points: PR review with severity tiers, STRIDE/OWASP scans per PR plus full-repo audits, lint autofix, dependency + secret sweeps, nightly docs + missing-tests jobs, API contract drift detection, wiki regeneration. Each is a published workflow you clone and tune. Not glamorous; extremely high ROI.</p>
<h2>Where factories fail</h2>
<ul>
<li><strong>Review collapse.</strong> Throughput without review capacity just moves the pile-up from writing to reviewing. Fix: preview environments with traces so reviewers merge on <em>seen behavior</em>, not on reading a thousand lines — plus severity-tiered automated review in front of humans.</li>
<li><strong>Goodhart gaming.</strong> Tell agents to maximize a test score and they will — StrongDM's agents famously wrote <code>return true</code>. Their answer was hidden scenario suites modeled on real customer usage plus AI-judged satisfaction, kept hidden from builders. Note the circularity Stanford's <a href="https://law.stanford.edu/2026/02/08/built-by-agents-tested-by-agents-trusted-by-whom/">critique</a> flags: when the builder and the inspector share blind spots, variety alone doesn't save you. Keep deterministic gates load-bearing and treat AI-judged scores as signal, not proof.</li>
<li><strong>Improvised infrastructure.</strong> Never let the agent write cloud config freestyle. Generate it deterministically from static analysis of the code, inside platform-team limits set once (IAM bounds, deployment policy). Agent autonomy bounded by rules a person wrote and can change.</li>
<li><strong>The dark-factory overreach.</strong> StrongDM's Level-5 "no human writes or reviews code" charter is a real production stance from a security-infrastructure vendor — and it surfaces unsolved liability, disclosure, and audit questions: no standard defines a sufficient satisfaction score, no procurement checklist covers shared builder/inspector blind spots. Run the spectrum of autonomy deliberately: bounded tasks autonomous, consequential actions human-gated, readiness-first rollout.</li>
<li><strong>Context poverty.</strong> Prompt engineering alone doesn't scale. Documentation quality directly bounds AI quality. Invest in ADRs, standards, and decision discipline (e.g. CI gates on decision records) — the factory is only as good as the context behind it.</li>
</ul>
<h2>How to build one (pragmatic order)</h2>
<ol>
<li><strong>Stand up a conveyor.</strong> One service, intake → plan → build → review, isolated env per change. <code>rig up conveyor</code> locally or one repo with preview environments. Prove the handoff path before adding stations.</li>
<li><strong>Add the deterministic gates.</strong> Tests, lint, type checks, secret/CVE scans, contract drift — as blocking checks, not suggestions. This is your quality floor.</li>
<li><strong>Fix review economics.</strong> Severity-tiered auto-review + running preview environments with traces. Target: reviewer confirms behavior in minutes instead of reading diffs for an hour.</li>
<li><strong>Lock the utilities.</strong> Centralized credentials, model routing, spend budgets with blocking rules, execution traces. Least-privilege by default; audit trail on every agent action.</li>
<li><strong>Close the learning loop.</strong> Production findings → next plan. Router learns task→model mapping. Incident correlates with the PR that caused it. Start with one feedback edge (e.g. dogfood findings into planning), then add more.</li>
<li><strong>Scale autonomy by station.</strong> Well-defined measurable tasks go fully autonomous; judgment-heavy stations keep human gates. Maturity is gradual and specific to your readiness — never a flag day.</li>
</ol>
<h2>The engineer’s job, restated</h2>
<p>No one starts with a fully autonomous factory, and no one should aim to install one. The role shift is the point: engineers stop being the sole custodians of building software and become responsible for building the factories that build it — standards, guardrails, acceptance criteria, and business outcomes. As the Cortex team <a href="https://www.cortex.io/post/what-is-an-ai-software-factory">puts it</a>: from working inside the system to designing the system itself.</p>
<p>Start with a conveyor, keep a human on publish, and instrument everything. The factory compounds.
